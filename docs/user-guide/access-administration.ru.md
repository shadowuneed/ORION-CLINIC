# ORION Clinic — управление подразделениями и доступом

Этот документ описывает локальный синтетический срез Phase 2C. Он предназначен
для функциональной проверки версионной модели доступа. Он не является
утверждённым регламентом клиники и не разрешает использовать реальные данные.

## 1. Что делает экран

Экран `/access/manage` доступен только интерактивному пользователю, у которого в
одном явно выбранном действующем назначении есть итоговое разрешение
`access.manage`. На экране администратор может:

- создать подразделение организации и филиала;
- выпустить новую версию названия, типа или статуса подразделения;
- выдать сотруднику назначение с одной или несколькими ролями;
- выпустить новую версию назначения: изменить роли, срок и точечные правила;
- отозвать назначение без удаления его истории.

Каждая команда требует текстовое основание. Корневые записи, версии и журнал
аудита не редактируются и не удаляются. Повтор той же команды с тем же ключом
идемпотентности возвращает прежний результат; другой payload с тем же ключом
отклоняется.

## 2. Как открыть

1. Запустите ORION командой `START_ORION.bat` и войдите в локальный контур.
2. Откройте **«Мой доступ»** и убедитесь, что выбран нужный рабочий контур.
3. Нажмите **«Управление доступом»** или откройте `/access/manage`.
4. Если действующих назначений администратора несколько, добавьте к адресу
   `?assignmentId=<идентификатор>`; ORION не объединяет их права.

Пользователь без `access.manage` не получает содержимое административного API.
Сервисная роль не может открыть интерактивный экран.

## 3. Подразделения

Кнопка **«Новое отделение»** создаёт неизменяемый корень и версию 1. Код корня
после создания не меняется. Кнопка **«Изменить»** создаёт следующую версию;
предыдущая остаётся в D1.

Текущее подразделение, из которого администратор получил `access.manage`, нельзя
отключить той же сессией. Это предотвращает случайное самоблокирование и не
заменяет будущий процесс двухстороннего одобрения.

## 4. Назначения сотрудников

Кнопка **«Выдать доступ»** предлагает только сотрудников текущего филиала, у
которых ещё нет действующего назначения в выбранном подразделении. Выберите:

- роли организации;
- начало и, при необходимости, конец срока;
- точечные добавления или запреты;
- основание изменения.

Явный запрет всегда сильнее базового или добавленного разрешения. Роль `service`
нельзя смешивать с интерактивными ролями. Изменение и отзыв создают новую версию;
физического удаления назначения нет.

Администратор не может изменить или отозвать назначение, которым авторизована
его текущая команда. Для такого изменения требуется другой действующий
администраторский контур.

## 5. Каталог пациентов после миграции

Семейство `/api/patients` больше не принимает роль членства как достаточное
основание. Сервер выбирает ровно одно действующее назначение и проверяет итоговые
разрешения:

| Операция | Требуемое разрешение |
|---|---|
| список и карточка | `patient.directory.read` |
| создание/изменение/архив и фото | `patient.profile.write` |
| создание приёма | `encounter.manage` |

Если доступных контуров несколько, API возвращает нейтральный `409` и список
только доступных назначений. Интерфейс просит выбрать одно и передаёт
`accessAssignmentId` во все ссылки и команды. Права разных контуров не
складываются.

## 6. Локальная проверка

```powershell
cd "C:\Users\profm\OneDrive\Документы\ChatGPT\ORION-CLINIC"
pnpm db:migrate:local
pnpm db:bootstrap:local
pnpm exec vitest run lib/domain/access-administration.test.ts lib/repositories/access-administration.test.ts lib/auth/patient-directory-access.test.ts app/api/access/admin/route.test.ts app/access/manage/access-administration-workspace.test.ts --no-file-parallelism --maxWorkers=1
pnpm verify:ci
```

Дополнительно откройте `/access/manage`, проверьте открытие и отмену трёх форм,
затем `/patients`. Ссылки карточек должны содержать выбранные `facilityId` и
`accessAssignmentId`. Не сохраняйте тестовое изменение доступа без заранее
определённого сценария возврата.

## 7. Нереализованные производственные границы

- промышленный OIDC/SAML, MFA, отзыв сессий и кадровое provisioning;
- двухстороннее одобрение опасных административных изменений;
- break-glass и сервисные credentials;
- глобальный долговечный security-event sink для доскоупных отказов;
- миграция остальных клинических API с `memberships.role`;
- регламент периодического пересмотра и автоматического истечения доступов.

Текущий срез остаётся локальным и синтетическим. Сам факт прохождения тестов не
является медицинской, юридической или эксплуатационной приёмкой.
