# ORION Clinic — подразделения, роли и просмотр собственного доступа

Этот документ описывает локальный синтетический срез Phase 2B. Он нужен для
проверки модели доступа до выбора промышленного поставщика удостоверений,
настройки MFA и допуска реальных данных пациентов.

## 1. Что реализовано

ORION хранит в D1:

- подразделение внутри конкретной организации и филиала;
- неизменяемую основу назначения сотрудника в подразделение;
- последовательные версии назначения и отдельную текущую голову;
- одну или несколько ролей, явные дополнительные разрешения и запреты;
- срок действия, статус, источник, автора и причину изменения.

Текущая версия рассчитывается на сервере. Браузер не является источником
полномочий и не может передать себе роль.

## 2. Роли

Стабильный каталог текущего среза:

| Код | Название | Базовое назначение |
|---|---|---|
| `doctor` | Врач | Приём, пациенты, направления, запись, наблюдение и связь в назначенном контуре |
| `nurse` | Медсестра | Назначенные показатели, планы наблюдения и задачи связи |
| `registrar` | Регистратор | Реестр, демография, запись, очередь и организационная связь без протокола |
| `administrator` | Администратор организации | Настройка доступа и аудит без автоматического клинического доступа |
| `medical_lead` | Медицинский руководитель | Проверка клинических правил и ограниченный надзор |
| `auditor` | Аудитор | Минимизированный журнал аудита |
| `service` | Сервисная учётная запись | Только узкая серверная интеграция, без интерактивного рабочего места |

Базовая роль не отменяет проверки организации, филиала, отношения к пациенту,
цели, состояния записи и действующего согласия. Явный запрет имеет приоритет над
базовой ролью и дополнительным разрешением.

## 3. Экран «Мой доступ»

1. Запустите ORION и войдите через локальный контур Sites.
2. В общей навигации откройте **«Мой доступ»** или адрес `/access`.
3. Проверьте организацию, филиал, подразделение, роль, срок и источник.
4. В блоке разрешений зелёным отмечены итоговые разрешения выбранного контура;
   остальные показаны как неразрешённые.
5. Если назначений несколько, сначала выберите один рабочий контур. ORION не
   складывает права разных подразделений или филиалов.

Страница только для чтения. Она не показывает список сотрудников, внутренние
идентификаторы пользователя и членства или сырые правила `allow`/`deny`.
Пользователь с итоговым разрешением `access.manage` видит отдельную ссылку
**«Управление доступом»**. Административные команды и их ограничения описаны в
[`access-administration.ru.md`](access-administration.ru.md).

## 4. Безопасные состояния

| Состояние | Поведение |
|---|---|
| Нет Sites identity | API возвращает `401`; защищённая страница запускает штатный вход |
| Нет активного назначения | Доступ не выдаётся; показывается обращение к администратору |
| Несколько назначений без выбора | Требуется явный выбор; права не объединяются |
| Выбран чужой или недоступный ID | Контур не раскрывается и не открывается |
| Истёкший, отозванный или отключённый контур | Исключается из действующих назначений |
| Только роль `service` | Интерактивный вход запрещён |
| D1 недоступна или версия повреждена | Проверка закрывается безопасно, полномочия не выдаются |

## 5. Локальная проверка

Минимальная синтетическая настройка создаёт подразделение **«Общая медицина»**
и назначение роли **«Врач»** для локального пользователя. Повторный запуск
bootstrap не создаёт дубликатов.

```powershell
pnpm db:migrate:local
pnpm db:bootstrap:local
pnpm exec vitest run db/access-governance.schema.test.ts lib/domain/access-governance.test.ts lib/auth/access-governance.test.ts lib/repositories/access-governance.test.ts app/api/access/route.test.ts app/access/access-workspace.test.ts --no-file-parallelism --maxWorkers=1
```

Проверка целостности локальной базы:

```powershell
pnpm exec wrangler d1 execute orion-clinic-local --local --command "PRAGMA quick_check; PRAGMA foreign_key_check;"
```

## 6. Что этот этап намеренно не заявляет

- Промышленный OIDC/SAML, MFA, отзыв сессий и жизненный цикл аккаунта не выбраны;
  это решение `DEC-009` клиники и службы безопасности.
- Административный экран и команды реализованы только для локального
  синтетического контура; это не заменяет утверждённый процесс кадрового доступа.
- Семейство каталога пациентов переведено на явно выбранное назначение и итоговые
  разрешения. Остальные клинические API пока используют прежние проверенные
  матрицы `memberships.role` и должны мигрироваться по одному семейству.
- Сервисные аккаунты, break-glass, глобальный журнал доскоупных отказов и
  периодический пересмотр доступов остаются отдельными задачами.
- Этот срез использует только искусственные локальные данные и не разрешает
  работу с реальными пациентами.

Следующий безопасный шаг Phase 2 — по одному переводить оставшиеся защищённые
семейства API и ограничения D1 на выбранное назначение и итоговое разрешение,
сохраняя прежние проверки пациента, цели, согласия и состояния записи.
