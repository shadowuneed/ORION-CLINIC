## 1. Вывод

Текущая платформа не реализует полный процесс из сообщений руководителя клиники.
До этого checkpoint фактически был реализован только клинический вертикальный
срез приёма: карточка пациента, encounter, согласия, локальный STT, расшифровка,
восемь разделов записи, предложения ИИ с решением врача, протокол и комплект
файлов. Фазы 4–8 из мастер-плана отсутствуют как рабочие модули и не должны
показываться как готовые.

## 4. Дефекты текущего пользовательского пути

| Дефект | Причина | Решение этого checkpoint |
|---|---|---|
| На `/live` решения выглядели как чекбоксы, но не нажимались | input намеренно имел `disabled`, а экран не давал выполнить D1 consent command | заменить псевдочекбоксы на отдельные явные действия care/transcript/local STT/audio retention с RU/KK, optimistic version и D1 reload |
| Кнопка STT всегда была заблокирована при одном отсутствующем решении | UI показывал только общий текст «не хватает согласий» | показывать каждое решение, его версию/отказ и точный список недостающих условий |
| Выход мог выполняться внутри вложенного окна | sign-out link не задавал top-level navigation | добавить `target="_top"`, сохранить официальный Sites sign-out route и не скрывать выход на мобильном экране |
| «Структурированная запись» выглядела как непонятное окно | отсутствовало объяснение цели, шагов и прогресса | назвать блок «Клиническая запись · 8 разделов», показать инструкцию, прогресс и причину недоступности проверки пустого раздела |

## 5. Правильный порядок дальнейшей реализации

1. Закрыть и проверить текущий encounter slice: согласия → STT → коррекция
   ролей/текста → AI drafts → врачебная проверка → протокол → документы.
2. Реализовать Phase 4 локально на D1: направления, назначения анализов/ЭКГ,
   results и manual reconciliation. Это следующий продуктовый модуль, а не
   заглушка навигации.
3. На подтверждённом referral/order построить Phase 5: расписание, выбор реального
   source slot, подтверждение записи и электронная очередь.
4. Добавить Phase 6: диагноз/registry decision, versioned care plan, follow-up
   tasks, cohort и nurse worklist.
5. Добавить Phase 7 через provider-neutral outbox; подключать реальный канал
   только после подтверждения бизнес-аккаунтов, шаблонов и согласий.
6. Добавить Phase 8: наблюдения, утверждённые правила риска, doctor-confirmed
   transfer и acknowledgement принимающей стороны.

## 6. Запрещённые заявления

До прохождения соответствующих acceptance gates нельзя заявлять, что ORION:

- автоматически записывает пациента к реальному врачу;
- отправляет направление, анализ, ЭКГ или сообщение во внешнюю систему;
- ставит пациента на реальный диспансерный учёт;
- определяет диабет, назначает лекарство или переводит пациента без врача;
- уведомляет реальную больницу или создаёт production «цифровой двойник»;
- готов к реальным медицинским данным или production deployment.
