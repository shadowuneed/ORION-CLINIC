# ORION Clinic — план оставшихся задач

Дата: 28.09.2026. План после текущего UI/login checkpoint. Это перечень следующих
работ, а не разрешение на деплой, новые права сотрудников или изменения основной БД.
Каноническое состояние и доказательства: `../MASTER_PLAN.md`, начало §13, §15–16.

## Что уже сделано и не нужно делать заново

- Компактный центр событий с данными существующих разделов; аналитика по кнопке.
- Сводка Groq по агрегированным счётчикам: настоящий ответ проверен, клинические
  тексты и сведения о пациентах этим запросом не передаются.
- Анатомическая иллюстрация с интерактивными сохранёнными измерениями и источником.
- Постоянный слой медицинской анимации входа/выхода маршрута и контрастные темы.
- Личный локальный вход шести существующих сотрудников, переключение и выход.
  Врач, медсестра и сотрудник без назначения проверены раздельно.

Это рабочий локальный checkpoint. Он не равен онлайн-релизу, полной изоляции
сохранённого аудио или завершённому мобильному приложению. Новые вымышленные записи
ради заполнения экранов не добавлять; существующие записи отображать достоверно.

## Очерёдность

| Этап | Приоритет | Результат | Зависимость |
|---|---|---|---|
| 1. Приёмка текущего интерфейса и входа | P0 | Предсказуемая работа основных экранов для разных сотрудников | Текущий checkpoint |
| 2. Сохранность записи и материалов | P0 | Восстановление своего приёма без чужих материалов и потери записи | Личный вход |
| 3. Карточка и центр уведомлений | P1 | Точное событие → пациент → конкретное действие | Этап1; постоянное серверное состояние |
| 4. Расписание и очередь | P1 | Полный управляемый путь записи, переноса и обслуживания | Действующие scoped API |
| 5. ИИ и длинный приём | P1 | Проверяемые подсказки, не теряющие ранний контекст | Этап2; источники/версии |
| 6. Закрытый онлайн-пилот | P1, отдельный выпуск | Защищённая работа с другого устройства | Этапы1–2, проверенные ключевые сценарии |
| 7. Отдельное мобильное приложение | P2, параллельная основа | Пациент видит только явно выданные ему данные | Защищённый пациентский API; этап6 для удалённой приёмки |
| 8. Внешние интеграции и клинический допуск | Отдельные ворота | Подтверждённые реальные обмены и эксплуатация | Договоры/решения клиники, этап6 |

P0 — сначала закрыть до расширения эксплуатации. P1 — ближайшие продуктовые
итерации. P2 — отдельный поток, не подмена веб-адаптива мобильным приложением.

## 4. Завершить расписание и очередь

Существуют локальные резерв, подтверждение, отмена/no-show и переходы талона.
Новая доска пока показывает ограниченную выборку, а не гарантированно всю очередь.

- [ ] **QUEUE-01:** серверная постраничная очередь с точной областью доступа,
  корректными счётчиками и согласованным порядком при конкурентных изменениях.
- [ ] **QUEUE-02:** доверенная фоновая обработка истёкших резервов с журналом;
  повторный запуск не освобождает подтверждённую запись и не делает дубль.
- [ ] **QUEUE-03:** перенос записи, лист ожидания и явное назначение освободившегося
  слота; правила приоритета и исключений согласовать, не подменять их догадкой ИИ.
- [ ] **QUEUE-04:** сквозная приёмка наполненной очереди двумя сотрудниками:
  направление → слот → подтверждение → прибытие → вызов → обслуживание → завершение;
  отдельно отмена, неявка, конфликт и повтор запроса.

**Готово, когда:** действия видны после перезагрузки/перезапуска, двойное бронирование
невозможно в проверенных гонках, истёкшие резервы обрабатываются автоматически.
Подключение внешнего расписания — отдельная интеграция, не часть локального успеха.

## 8. Внешние системы и клиническая эксплуатация

- КМИС/LIS/ЭКГ: договорённый формат, отправка, подтверждение, отмена, повтор,
  исправленные результаты и сверка расхождений.
- SMS/мессенджеры/звонки: согласованный провайдер, согласие канала и доказательство
  доставки; локальное намерение сообщения не является доставкой.
- ЭРДБ/ПУЗ/льготы, юридическая подпись и межучрежденческий обмен: отдельные
  источники полномочий и решения клиники. Нельзя объявлять подключёнными заглушки.
- Утверждённые тревожные пороги, ответственные, SLA и врачебная приёмка до работы
  с настоящими медицинскими данными. До этого сохраняется текущий ограниченный контур.

## Организация следующих итераций

Три параллельных потока: **интерфейс/браузерная приёмка**, **сервер/сохранность/очередь**,
**ИИ/контекст/тесты**. Интеграционный ответственный принимает изменения вместе и
ведёт Verification ledger; общие файлы заранее распределяются, права не расширяются
ради прохождения тестов. Пациентский API/мобильный клиент можно готовить отдельно,
но подключать только после прохождения своих серверных границ.

Первый следующий пакет: UI-01/02 + AUTH-01 + проектирование/интеграция REC-01.
После него — один доказанный сквозной результат очереди, затем длинного ИИ-приёма.
Не запускать все незавершённые эпики одновременно и не заменять функциональную
приёмку очередной декоративной переработкой. Сроки оценивать по этим пакетам
после проверки P0, а не обещать готовность всей платформы одной датой.
