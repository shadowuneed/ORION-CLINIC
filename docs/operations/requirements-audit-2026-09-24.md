В проекте есть настоящие локальные DB-backed процессы, а не только экраны: восемь разделов протокола, врачебная проверка, назначения и ручные результаты, локальные записи/очередь, подписанные планы наблюдения и задачи, очередь намерений уведомления, версионные измерения. Но полный маршрут из требований — от первого обращения через внешнюю запись и диспансерный учёт до стационара — **не завершён**.

Нельзя считать платформу готовой к клиническому production или публичной многопользовательской работе по наличию этих модулей, зелёному build либо публикации веб-оболочки. Индивидуальный вход в основном runtime, защита локальных записей разных сотрудников, инфраструктура закрытого пилота, внешние адаптеры и клинические решения остаются отдельными воротами.

Значения ниже: **локально реализовано** — найден рабочий серверный путь и сохраняемая модель, но не заявлена внешняя/клиническая приёмка; **частично** — работает только указанная часть требования; **не реализовано** — требуемого end-to-end процесса в исследованном срезе нет; **внешняя зависимость** — нужны решения клиники/контракт/источник, которые нельзя достоверно заменить тестовым успехом. Номера строк — навигационные указатели для этого среза, после изменений могут сместиться.

## Два следующих полезных инженерных шага

Оба шага можно строить на искусственных данных без внешних клинических интеграций. Они **не заменяют** первоочередные ONLINE-1B/1C/1D. Порядок ниже следует текущему продуктовому backlog плана; решение о параллельном выполнении — у основного исполнителя.

### 1. D-R3 — локальный checkpoint реализован, приёмка 24.09.2026

Исходная проблема: врач повторно переносил текст вручную, а происхождение
назначения не сохранялось. Теперь schema принимает только selector ID/версии;
текст принятого источника и ID решения выбирает сервер. UI даёт проверить поля,
сохранить черновик и затем открыть его по постоянной ссылке. Существующие ручные
направления продолжают работать. Следующий список — acceptance-контракт этого
checkpoint, не утверждение о подключённой КМИС.

Ограниченный результат:

- Кнопка только для доступной, актуальной рекомендации, принятой или отредактированной врачом; сервер получает ID, а не доверяет присланному клиентом тексту/статусу.
- Точная связка patient/encounter/facility/accessAssignment и неизменяемой версии исходного AI-материала + решения врача. Основание сохраняется в черновике и hash идемпотентной команды.
- Врач видит/редактирует услугу, показания, приоритет, специальность до сохранения. Создание остаётся `draft`; утверждение назначения отдельно; внешнего отправления нет.
- Тесты: одинаковый повтор → тот же результат; другой payload того же ключа → конфликт; чужой пациент/приём/assignment, отвергнутый/устаревший источник, отозванное согласие/права и гонка до commit → отказ без утечки; ручной путь продолжает работать. DB reload/reopen сохраняет provenance.

### 2. D-R2 — подтверждаемая накопительная информация длинного приёма

Почему: `getCanonicalTranscript()` ограничен 24 последними финальными/исправленными сегментами. AI-запись может заменить `empty/ai_draft` разделы; защита `clinician_edited/reviewed` есть, но сама по себе не удерживает раннюю аллергию/лекарство/отрицание в новом непроверенном черновике.

Ограниченный результат:

- Накопительный набор фактов/черновиков с источником и версией каждого сегмента, входным hash и явной обработкой исправлений, отзыва и противоречий. Простая конкатенация старого и нового текста не является корректным слиянием.
- Старый AI-факт не получает статус врача; утверждённый/отредактированный раздел не перезаписывается. Нерешённое противоречие видно врачу; отсутствие сведений не заполняется догадкой.
- Тесты разговора длиннее 24 сегментов: ранняя аллергия и отрицание, дозировка/единицы, исправление раннего сегмента, повторная доставка/устаревший результат, разные пациенты/назначения, отзыв согласия, отказ провайдера. Перезапуск сохраняет источники и врачебные решения, а не только текст в памяти браузера.

Ближайшие меньшие задачи после этих шагов: адресный scoped-поиск пациента вне первых 200 измерительного списка; постоянная версионная связь «измерение/результат → задача» с отдельным решением о завершении; перенос записи/лист ожидания/контролируемый worker сроков; единая read-only хронология без фиктивного hospital-transfer.

## Внешние решения и допуск к запуску

| Что требуется | Владелец по плану / минимальное подтверждение |
| --- | --- |
| КМИС, лаборатория, расписание, ЭКГ | `DEC-001/002/005`: clinic IT + vendor; продукт/версия, sandbox, auth/scopes, source of truth, форматы, acknowledgement, повторы и сверка. |
| ЭРДБ/ПУЗ/льготные лекарства | `DEC-003/004/014`: клиника/health authority, clinical lead, pharmacy/IT; точный смысл системы и разрешённый контракт, право записи/чтения, источник льготы и отпуска. |
| Пациентские каналы | `DEC-012`: clinic operations; бизнес-аккаунт, шаблоны/язык, consent/destination verification, callback authenticity и ручной fallback. |
| Критический статус и стационар | `DEC-006/007/013/015`: clinical committee, product/clinical lead, clinic leadership/IT; подписанные правила/SLA, принимающие организации, минимальный пакет и явный acceptance. |
| Правовая эксплуатация | `DEC-010/011`: legal/clinical lead; retention, обработка аудио/ИИ, правовой статус подписи и разрешения на данные. Все данные до отдельного допуска остаются искусственными. |

Для закрытого онлайн-пилота отдельно нужно завершить индивидуальные credentials/provisioning/reset/throttling и подключить session foundation к общему SSR/API (`ONLINE-1B`), изолировать локальные записи/старые вкладки и legacy recovery (`ONLINE-1C`), затем подтвердить долговременные DB/object storage, TLS/secrets, миграции, backup/restore, наблюдаемость и защищённый постоянный STT-сервис (`ONLINE-1D`). Два врача одной роли должны оставаться разными субъектами. Общая development-учётная запись и выбор роли в UI этого не обеспечивают.

Запрос на Vercel не закрывает эти пункты автоматически: действующие D1/R2 bindings и STT требуют реального согласованного backend/runtime, а не одной успешно опубликованной страницы. Данный аудит не создавал cloud resources, не проверял deployment и не разрешает публично выставлять development authentication. Финальная проверка — независимые аккаунты/браузеры, scoped-отказы после logout/revoke, сохранение/перезапуск/restore и полный синтетический маршрут (`ONLINE-1F`), затем отдельная клиническая приёмка Phase 10.
